## Failure

The supplied IntelliJ launch failed at 16:32:50 during Spring Data repository discovery:

```text
java.lang.ClassFormatError: Invalid method Code length 0 in class file
io/sitprep/sitprepapi/gamification/HouseholdTokenSeen$Key
```

The launch used Java 21.0.3 and `sitprepapi 2/target/classes`. The JVM rejected the class before datasource/schema startup. The earlier commons-logging warning was not the cause of this failure.

## Evidence And Cause

- `javap -v` on the actual failing class showed its Lombok-generated public no-argument constructor with a Code attribute but no instructions. Other methods were present. This is invalid executable bytecode, not a missing Java source constructor.
- The malformed class was 2,243 bytes, modified at 16:22:33. Its SHA-256 was `193e2fc0b5aa0ff4c5d15a9134a4ee59c3e651a680b07abdbe4ac7ef5695fde9`.
- HouseholdTokenSeen.java had not changed since `feed367` (Readiness Tokens T1, 2026-10-03). That feature's lane is already closed; its original execution notes are under the FE Readiness Tokens archive.
- A JVM audit loaded application classes without initializing them, then inspected constructors, methods, and generic interfaces. Shared output: 1,223 classes checked, 180 class-loading/metadata failures. Some failures were downstream references to the same malformed type; this is not a claim of 180 independently damaged files. Failures included Group, UserInfo, AlertHistory, and multiple unrelated DTO/entity classes.
- An isolated Maven compilation of the unchanged source produced 1,234 classes, all passing the same JVM audit. The regenerated Key constructor contains `aload_0`, `invokespecial Object.<init>`, and `return`.
- IntelliJ's compile server and VS Code Java language-server processes were running. VS Code's installed Java extension defaults automatic building to true, and the workspace had no override. IntelliJ's annotation processor configuration already points to the existing Lombok 1.18.36 jar; this is not the older missing-processor-version incident.

Confirmed cause: malformed/stale shared compiled output. Likely producer: IDE automatic/incremental compilation into the same Maven output directory. This workspace already documents that pattern in FE SYSTEM_TRAPS_AND_PATTERNS T-14 and T-90. The exact process that wrote the malformed files was not observed, so do not attribute it to a particular feature agent or a proven compiler defect.

## Recovery

1. Preserved the malformed gamification output and all original application `.class` files in `/private/tmp/sitprep-bytecode-recovery.37dr5l/`.
2. Set workspace `.vscode/settings.json` to `java.autobuild.enabled: false`. Existing autosave/hot-exit settings were preserved. Java automatic build control is documented by [the Java extension](https://github.com/redhat-developer/vscode-java/blob/main/README.md).
3. Copied source, pom.xml, Maven wrapper, and wrapper configuration into that isolated scratch directory. No shared-target Maven clean was run, and no IDE processes were killed.
4. Ran Java 21 Maven offline compile and focused tests from the scratch copy.
5. Compared the source tree and pom.xml with the live backend immediately before restoring output: both matched. No original-only `.class` files needed removal.
6. Restored only regenerated `.class` files into the IntelliJ application's existing `target/classes` via filtered rsync. Runtime resources/local configuration were preserved; no database or migration operations were performed as part of recovery.
7. Verified the restored live target using the same JVM audit: 1,234 classes checked, zero failures. Key class SHA-256 after repair: `ea056bbbd13da363047ad5bec75609f453238176118119a092bee6adff39728f`.

The scratch copy holds source/configuration and may include local credentials; keep it local, do not upload or commit it. It is a temporary recovery artifact, not a long-term backup.
